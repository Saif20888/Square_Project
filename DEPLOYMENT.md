# Deploying the SQUARE Group IT Operations Portal

Two pieces ship separately:

- `square-backend` — Spring Boot API (Java 21), talks to PostgreSQL
- `square-frontend` — React app built by Vite into static files

---

## 1. Before you start

You need:

- A PostgreSQL database, with a dedicated user for the app (not the `postgres`
  superuser).
- A hostname for the API and one for the frontend, both served over **HTTPS**.
- Somewhere to store environment variables (your host's config panel, systemd
  unit, Docker env file, …). Never commit them.

---

## 2. Backend configuration

Everything sensitive is read from the environment. `src/main/resources/application.yaml`
holds development defaults only; `application-prod.yaml` deliberately has **no
fallbacks**, so a missing variable stops the app instead of silently starting
with a development password.

Copy `square-backend/.env.example` and fill it in:

| Variable | Required | Meaning |
| --- | --- | --- |
| `SPRING_PROFILES_ACTIVE` | yes | Must be `prod` |
| `DB_URL` | yes | e.g. `jdbc:postgresql://db-host:5432/square_db` |
| `DB_USERNAME` | yes | Dedicated app user |
| `DB_PASSWORD` | yes | Strong generated password |
| `CORS_ORIGINS` | yes | Frontend origin, e.g. `https://portal.example.com` |
| `ADMIN_USERNAME` | first boot | Username of the first System admin |
| `ADMIN_PASSWORD` | first boot | At least 12 characters |
| `SERVER_PORT` | no | Defaults to 8080 |

`CORS_ORIGINS` accepts a comma-separated list. It must match the frontend
origin **exactly** (scheme + host + port) or the browser blocks every API call.

### The schema builds itself

Nothing manual is needed. **Flyway** owns the schema: on startup it runs the
files in `src/main/resources/db/migration` in version order, exactly once each,
and records what it ran in a `flyway_schema_history` table.

Point the app at an empty database and `V1__initial_schema.sql` creates all
eight tables. Hibernate then runs with `ddl-auto: validate`, which only checks
that those tables match the entities — it never writes.

Two cases, both handled automatically:

| Database | What happens |
| --- | --- |
| Empty | V1 runs and builds the schema |
| Already has the tables (created by the old `ddl-auto: update`) | Recorded as already at V1 and **not** re-run, thanks to `baseline-on-migrate` |

### Changing the schema later

Never edit `V1__initial_schema.sql` — Flyway checksums applied migrations and
will refuse to start if one changes. Add a new file instead:

```sql
-- src/main/resources/db/migration/V2__add_asset_disposal_note.sql
ALTER TABLE assets ADD COLUMN disposal_note varchar(255);
```

Change the entity and the migration together. Because `ddl-auto` is `validate`
in development too, forgetting the migration fails immediately on your own
machine rather than at deployment time. Name files `V<n>__<description>.sql`
(two underscores).

> `V1__initial_schema.sql` was generated by Hibernate from the entity classes,
> then verified column-for-column against the live database — all 84 columns
> matched. It is not hand-written.

### First sign-in

If the database has no users, the app creates one System admin from
`ADMIN_USERNAME` / `ADMIN_PASSWORD` and nothing else. Demo employees, tickets
and assets are created only under the `dev` profile — the seeding runner is
annotated `@Profile("!prod")` because its passwords are visible in the source.

**Sign in and change that password immediately.** Changing a password revokes
every other session for that account.

### Run it

```bash
SPRING_PROFILES_ACTIVE=prod ./mvnw clean package
SPRING_PROFILES_ACTIVE=prod java -jar target/backend-0.0.1-SNAPSHOT.jar
```

## 3. Frontend configuration

Vite inlines environment variables **at build time**, so set them before
building and rebuild after any change.

Copy `square-frontend/.env.example` to `.env.production`:

```
VITE_API_BASE=https://api.example.com
```

No trailing slash. Leave `VITE_ENABLE_DEMO` unset — setting it turns the seed
data fallback back on, which hides real backend outages behind fake data. In a
production build the app instead shows "Server unreachable" and refuses to sign
anyone in from the local seed list.

```bash
npm ci
npm run build      # outputs to dist/
```

Serve `dist/` from any static host or CDN.

## 4. HTTPS is mandatory

Sign-in posts a password and every later request carries a bearer token. Over
plain HTTP both are readable by anyone on the network, which defeats the
password hashing and the token store entirely.

Terminate TLS at your platform's load balancer or a reverse proxy. An nginx
sketch:

```nginx
server {
    listen 443 ssl;
    server_name api.example.com;

    ssl_certificate     /etc/letsencrypt/live/api.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/api.example.com/privkey.pem;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

Redirect port 80 to 443, and serve the frontend over HTTPS too — a page loaded
over HTTPS cannot call an HTTP API (mixed content).

## 4b. Roles, monitoring and the audit trail

**Authorization** is enforced on the server by `@RequiresRole` plus
`RoleInterceptor`, not by the UI. Reads (tickets, assets, users, office and
department lists) are open to any signed-in person; everything else is
restricted:

| Area | Who |
| --- | --- |
| Work a ticket (accept / reject / resolve) | IT Team |
| Asset lifecycle (loan, repair, receive, warranty) | IT Team |
| Scrap or assign an asset | IT Team, Superuser |
| Approve a pending assignment | Superuser |
| Onboarding, offboarding, password resets | Superuser |
| Offices and departments, import history | Superuser |
| Audit trail | Superuser |
| System health screen | System admin |

Editing a profile is limited to your own, and designation / department / unit
to the Superuser, so nobody can promote themselves. The System admin passes
every role check by design — see `Roles.isAdmin`.

**Health checks** live at `/actuator/health` and need no token, so a load
balancer or uptime monitor can read them. No other actuator endpoint is
exposed. Point your monitor there and alert when it stops returning `UP`.

**The audit trail** (`GET /api/audit`, Superuser and admin only) records
password resets and changes, onboarding, asset scrap and assign, and every
change to the office/department structure — who did it, their role at the
time, and when. Records are only ever written, never edited or deleted.

**Rate limiting** caps sign-in attempts at 20 per address per five minutes, on
top of the ten-minute lockout after five wrong passwords for one account. If
you run behind a reverse proxy, make sure it sets `X-Forwarded-For`, and add
rate limiting there too so abusive traffic never reaches the application.

## 5. Known limitations

Be aware of these before scaling up:

- **Sessions live in memory.** `TokenStore` keeps tokens in a map inside the
  process. Restarting the backend signs everyone out (the frontend detects the
  401 and returns them to the login screen). More importantly, **running more
  than one backend instance will not work** — a token issued by instance A is
  unknown to instance B. To scale horizontally, move sessions to Redis or switch
  to signed JWTs.
- **Tokens are stored in `localStorage`.** Convenient and survives reloads, but
  readable by any script running on the page, so an XSS bug becomes a session
  compromise. An httpOnly, Secure, SameSite cookie is stricter.
- **Rate limiting is in-process.** Like the session store, the counters live in
  one JVM's memory, so with several instances each enforces its own share of
  the limit. Proxy-level rate limiting is the real answer at that scale.
- **Frontend has no automated tests.** The backend suite covers authorization,
  sessions, validation and paging; the React side is still verified by hand.
- **The audit trail is not shown in the UI.** `GET /api/audit` returns it, but
  no screen renders it yet.

## 6. Post-deploy checklist

- [ ] `https://api.../api/tickets` returns **401**, not data, without a token
- [ ] Signing in over HTTPS works and the header shows "Postgres · live"
- [ ] The initial admin password has been changed from the bootstrap value
- [ ] Stopping the backend shows "Server unreachable" — **not** demo data
- [ ] Database backups are running and a restore has actually been tested
